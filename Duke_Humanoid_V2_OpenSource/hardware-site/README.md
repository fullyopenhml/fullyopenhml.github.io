# Duke Humanoid V2 — hardware documentation site

The hardware release for Duke Humanoid V2, built with
[MkDocs Material](https://squidfunk.github.io/mkdocs-material/). Its single job:
a stranger reads it and can build an identical robot.

The software is open elsewhere and is **not** duplicated here — `docs/software.md`
is a bridge page to the two code repositories.

## Run it locally

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

mkdocs serve          # live reload at http://127.0.0.1:8000
mkdocs build --strict # what CI runs; must exit 0
```

`--strict` turns broken internal links and missing nav targets into errors. Run
it before pushing.

## How the content is organised

| Path | What lives there |
| --- | --- |
| `mkdocs.yml` | Site config and the full nav. Every nav entry must point at a real file. |
| `main.py` | The `mkdocs-macros` module. Defines the BOM cost macros and the assembly-page helpers. |
| `docs/` | All page content. |
| `docs/data/` | BOM CSVs. **All cost figures are computed from here**, never typed into prose. `docs/data/README.md` is the column contract. |
| `docs/stylesheets/extra.css` | Four additions to the theme: parts table, step badge, checkpoint callout, pending-figure marker. |
| `docs/assets/images/` | Figures. Real photographs of the reference robot live here; every figure the site still needs is listed in `docs/assets/MANIFEST.md`. |
| `tools/` | The generators. `docs/data/*.csv`, `docs/reference/todo.md` and `docs/assets/MANIFEST.md` are all derived — see `tools/README.md`. |
| `.github/workflows/docs.yml` | Strict build on push and PR; Pages deploy from `main`. |

The page tree follows the order a builder works in: decide → buy → make →
assemble → wire → bring up. `docs/reference/` is lookup material, not a stage.

## Writing rules

These are not style preferences. They exist because this site tells people how
to build a 36 kg machine.

1. **Never invent a hardware fact.** A torque, wire gauge, screw length, print
   temperature or clearance that is not verifiable from a source goes in as a
   visible TODO, not as a plausible number:

   ```markdown
   !!! warning "TODO — 待填"
       <exactly what is missing, and who can supply it>
       *Owner: <role>*
   ```

   A page full of honest TODOs is acceptable. A page full of invented numbers is
   a safety hazard.

2. **Never hand-type a cost.** Call a macro. Costs live in `docs/data/`, and the
   CSVs there are generated by `tools/` — edit the source spreadsheet and re-run,
   do not patch a CSV in place.

   Never hand-list the files inside `bom_total([...])` either. Three pages once
   did, and they would have disagreed the moment a seventh parts file landed.

3. **Page prose is English.** The TODO admonition title is the one exception.

   Every TODO block needs an `*Owner:*` line. `tools/gen_punchlist.py` fails
   without one, and the punch list at `docs/reference/todo.md` is regenerated
   from those blocks — so a TODO added without an owner never reaches the list
   the team actually works from.

4. **Never write a real `![](…)` for an image that does not exist yet.** It fails
   `--strict` and it fails the whole site, not just your page. Use the figure
   placeholder convention documented on `docs/assembly/index.md` and add the row
   to the image manifest.

5. **Do not soften a known defect.** The BOM defects listed in `docs/bom/index.md`
   are published deliberately. Delete an entry when it is fixed, not before.

## Macros

Defined in `main.py`, called from pages as `{{ macro(...) }}`:

| Macro | Returns |
| --- | --- |
| `bom_subtotal(csv, subassembly=, part_class=, exclude_ids=)` | Formatted subtotal of one CSV |
| `bom_total(csv_names=, exclude_ids=)` | Whole-robot parts total. **Call it bare.** With no arguments it sums every parts CSV except the non-robot files listed in `main.py` |
| `bom_count(csv, ...)` | Number of matching part rows |
| `bom_qty(csv, ...)` | Sum of `qty_per_robot` |
| `bom_unpriced(csv)` | `part_id` list of rows with no usable price |
| `bom_priced_as_of(csv)` | Newest price date in the file |
| `data_file_exists(csv)` | Boolean, for gating prose |
| `money(x)` | USD formatting, one way, everywhere |
| `step(n, title)` | Numbered step heading with a badge |
| `checkpoint(text)` | A must-pass verification callout |

A macro whose CSV is missing returns a visible *not yet published* marker. That
is the correct output — do not work around it by typing the number in.

## CSS classes

`parts-needed` (wrap a step's parts table), `step-badge` (emitted by `step()`),
`checkpoint` (admonition type, also usable as `!!! checkpoint`), `pending-figure`
(emitted by the macros).

## Regenerating the derived pages

```bash
python tools/gen_punchlist.py       # docs/reference/todo.md
python tools/gen_image_manifest.py  # docs/assets/MANIFEST.md
mkdocs build --strict
```

Run both after any edit that adds, closes or moves a TODO block or a figure
placeholder. They are cheap and they are the only thing keeping the two lists
honest.

## Notes

- `docs/data/README.md` and `docs/assets/MANIFEST.md` are intentionally outside
  the nav; the `INFO` line the build prints about them is expected. `MANIFEST.md`
  is linked from the pages that need it.
- `git-revision-date-localized` is gated on the `GIT_REVISION_DATE` environment
  variable. It is off by default so that `mkdocs build --strict` also succeeds
  outside a git checkout; CI sets `GIT_REVISION_DATE=true` after fetching the
  full history, which is when page dates actually appear. To see them locally:

  ```bash
  GIT_REVISION_DATE=true mkdocs serve
  ```
